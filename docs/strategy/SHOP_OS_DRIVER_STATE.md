# Shop OS driver state

- **Outcome:** Make ShopOS's living repair order work flawlessly across every intended role: permitted users can create, find, own, hand off, quote, perform, and close work from the right queue on phone or desktop, without extra pages, reload-feeling transitions, or lost work. The signature is continuity without ceremony: the repair order stays present while only the applicable tool changes.
- **Current slice:** Row 60 is complete, merged, and deployed. A repair order whose every job has reached `done` or `canceled` no longer falls off Today: advisors and owners keep one ticket-level `Ready to collect` card carrying the exact `getTicketRingOut` balance, and selecting it mounts the existing payment/close tool inline on the board. The card leaves only when the server confirms the repair order is no longer open. Row 61 is the next lane: a repair order becomes unfindable the moment it closes, so the counter needs a tenant-scoped lookup that mounts closed work in place.

- **The post-diagnosis flow did not exist (PR #216):** the owner reported that an open repair order "only appears to let me add more diagnostics." Confirmed, in two parts. First, nothing could add an ad-hoc repair: the only paths onto a quote were a saved canned template and `diagnostic-time`, and the general add-job route at `app/api/tickets/[id]/jobs/route.ts` had been deliberately retired to a hard 404. Second, the findings editor was a **closed loop** — `storyMode` returned `authorization_only` (a dead sentence, no editor) whenever a diagnostic job had no session and no story, while the `manual_findings` editor required a story to already exist. Because `getDiagnosticsRelease()` returns `off` unconditionally in production, a counter-written diagnostic job never gets a session, so no shop in production could ever author a first story. The fix reorders the entitlement check ahead of the authorization-only case, and adds `createAdHocJob` + `POST /api/tickets/[id]/quote/jobs` — same auth, tenant scoping, client-key idempotency, 25-job limit and conflict semantics as the canned-job route, with the tier derived from work kind. `pendingStory` was narrowed so an authorization-only quote still sends.

- **The counter door can no longer double a repair order (PR #219, merged `f2557c2`):** `/intake` — the door the shop actually uses — posted with no client key, so a retry on shop Wi-Fi minted a second identical repair order and burned a second repair-order number. - **What #219 broke within minutes, and how the gate caught it (PR #222, merged `7fdb1e5`):** `lib/shop-os/quote-editor-draft.ts` bounded every id through a UUID pattern accepting only versions 1–5. Postgres `gen_random_uuid()` mints version 4, but **every client-key idempotency derivation in this codebase stamps version 8** — `quick-ticket.ts`, `canned-jobs.ts`, `quotes.ts`, `simple-work.ts`, and now `counter-ticket.ts`. So the moment counter repair orders carried a derived id, `quoteEditorDraftKey()` threw, both the save and restore paths swallowed it, and the unsaved-labor reload guard was silently **off for exactly the repair orders the shop writes at the counter** — a typed labor line lost with no console error and no failed request. One character, `[1-5]` → `[1-8]`, plus a codec test and a component test that both fail on the parent commit. Two lessons: a fail-soft `catch` that turns a storage failure into a quiet status line is invisible to every signal except a browser walking the journey; and this was never phone-only — `golden-phone` simply runs first and aborted the run before `golden-desktop` ever started, which is why desktop looked green.

- **Migrations, closed (no owner gate needed after all):** the fix was not to resurrect Drizzle's journal but to replace it. `scripts/db-migrate.mjs` applies the folder in filename order and records each file in `public.schema_migrations` with a checksum; `npm run db:migrate` and `db:status` now point at it, and the broken `db:generate` is gone. Re-running migrations was never the right shape — 45 of 51 are not re-runnable, so making them idempotent would have meant rewriting already-applied history.
